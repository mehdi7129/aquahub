AquaHub — reprendre le développement
Référence : préproduction 0.2.4

1. Commencer ici

Le dépôt contient le code de la GUI, de son agent et de son installateur.
Le bundle fournisseur, ses images et les configurations d’un client restent
externes. Aucun accès fournisseur n’est nécessaire pour compiler l’interface,
utiliser la démo ou exécuter les tests génériques.

Lire README.md, ARCHITECTURE.txt, SECURITE.txt et ETAT_ET_FEUILLE_DE_ROUTE.txt.
Pour modifier une action, remonter le flux : frontend/src/app.ts, pont natif
desktop/aquahub_desktop/app.py, dispatch agent/aquahub_agent/core.py, adaptateur
spécialisé. Les fixtures dans tests/ montrent les entrées et sorties attendues.

2. Poste de développement

Référence supportée : Debian 13 amd64 / GNOME, Python système 3.13.
Node.js doit satisfaire les contraintes du package-lock ; la compilation
frontend utilise esbuild et TypeScript. Node n’est pas requis chez le client.

Paquets de développement à prévoir, selon le poste :

  sudo apt install git nodejs npm python3 python3-gi python3-cairo \
    python3-gi-cairo gir1.2-gtk-3.0 gir1.2-webkit2-4.1 \
    build-essential pkg-config libgtk-4-dev dpkg-dev apt-utils gnupg \
    xvfb xauth libx11-6 libxtst6 dbus x11-utils desktop-file-utils

Ces commandes concernent uniquement le développeur. Elles ne sont pas le
parcours graphique de l’utilisateur final. Utiliser /usr/bin/python3 : les
bindings GI proviennent des paquets Debian. Un venv isolé classique ne les
voit pas automatiquement. L’agent n’a pas de dépendance pip.

Docker natif et le bundle ne sont pas nécessaires à la démo ni aux tests
génériques. Leur installation sur un banc est une opération séparée. Le
préparateur de kit nécessite des paquets/images précis déjà disponibles et
des droits sudo non interactifs ; lire PUBLICATION.txt avant son utilisation.

3. Récupérer et compiler

  git clone https://github.com/mehdi7129/aquahub.git
  cd aquahub
  cd frontend
  npm ci
  npm run check
  npm test
  npm run build
  cd ..

npm ci utilise les versions du lockfile. Le résultat est frontend/dist/.
Ce répertoire généré n’est pas versionné. Ne pas ouvrir uniquement index.html
dans un navigateur pour qualifier l’IPC : la vraie application est GTK/WebKitGTK.

4. Lancer la démo sans matériel

Depuis la racine du dépôt, avec un utilisateur normal :

  PYTHONPATH=agent:desktop /usr/bin/python3 -m aquahub_desktop \
    --demo --no-agent --socket /tmp/aquahub-demo-unused.sock \
    --state-dir ./local-private/demo

--demo choisit les données fictives du frontend et --no-agent empêche le
démarrage d’un agent. Le socket indiqué n’est relié à aucun agent installé.
Le dossier local-private/ est ignoré par Git. Le bandeau de démonstration
doit rester visible. Cette fenêtre ne prouve aucun état du matériel.

5. Exécuter les tests

  PYTHONPATH=agent:desktop /usr/bin/python3 -m unittest discover -s tests -q

Les tests génériques se lancent sans Docker ni drone. Les cas facultatifs
couvrent des lectures Docker, le contrat fournisseur sur transports interceptés
et les dialogues GTK/WebKit des exports. Ils exigent leurs opt-ins et
préconditions : bundle local explicitement indiqué ou affichage isolé selon
le cas. Rapporter les cas ignorés ; les commandes et le détail de chaque
précondition sont dans TESTS.txt.

Les tests d’installation compilent de petits helpers avec les en-têtes GTK4
et construisent un faux paquet. Ils n’installent pas ce paquet dans le système.
Lire leurs préconditions si le poste n’est pas Debian 13.

6. Travailler avec un vrai agent

Le démarrage normal du desktop peut sélectionner l’agent système déjà installé.
Ne pas l’utiliser par inadvertance pour un développement isolé. Un agent de
session possède son socket et son état propres ; il peut néanmoins piloter le
moteur Docker auquel son utilisateur a accès. Une isolation de chemins n’est
donc pas une isolation du matériel.

Pour une recette réelle, préparer un banc autorisé, une sauvegarde et les
preuves avant/après. Utiliser les options --socket, --state-dir et --bundle
de l’agent, puis --socket et --no-agent du desktop. Les options exactes sont
consultables sans lancer une opération :

  PYTHONPATH=agent:desktop /usr/bin/python3 -m aquahub_agent --help
  PYTHONPATH=agent:desktop /usr/bin/python3 -m aquahub_desktop --help

Ne pas exécuter le desktop en root. Ne pas copier des règles PolicyKit de
recette dans une installation client. Une lecture de paramètres SSH peut
demander une autorisation : la méthode protégée sert aussi à leur modification.

7. Où modifier quoi

Interface et confirmations : frontend/src/app.ts et styles.css.
Données métier UI : frontend/src/domain.ts ; transport et démo : bridge.ts.
Fenêtre, dialogues privés, archives : desktop/aquahub_desktop/app.py.
Client JSON et navigation : desktop/aquahub_desktop/bridge.py.
Routes et tâches : agent/aquahub_agent/core.py.
Socket serveur : server.py ; autorisations et redaction : security.py.
Docker natif : docker.py ; bootstrap du compte Portainer : portainer.py.
Configuration Aqua_Drones : drone.py ; archivage d’incidents : health_history.py.
Historique SQLite : store.py ; comparaisons réseau : network.py.
Exports de journaux : agent/aquahub_agent/log_exports.py pour la collecte,
desktop/aquahub_desktop/log_exports.py pour le fichier et le dialogue GTK.
Archives/mises à jour du bundle : updates.py et image_identity.py.
Mises à jour de l’application : app_updates.py ; installation indépendante
dans installer/application_upgrade.py. Ces deux canaux restent séparés.
Paquet hors ligne : installer/build_package.py, bootstrap.c, setup_helper.c,
finish.py et upgrade_guard.py. Le mode --application-only construit un
petit paquet de mise à niveau sans payload fournisseur ; consulter
PUBLICATION.txt pour son contrat et ses préconditions.

8. Ajouter une action sans contourner les contrôles

Définir les paramètres et les erreurs attendues ; décider si la méthode est
privilégiée. Enregistrer la méthode via register_handler. Garder les cibles
fermées, les arguments sous forme de tableaux et l’exécution longue dans une
tâche persistante. Ne pas créer de commande shell ou de proxy Docker générique.

Ajouter le test du comportement et du refus associé avant de raccorder la vue.
Une opération doit rester unique en cas de double-clic et son résultat doit
être retrouvé après reconnexion. Ne pas inventer un succès quand le retour
du service ou de l’appareil n’a pas été vérifié.

9. Versionner et livrer

La version visible est définie dans les modules __init__.py de l’agent et du
desktop. Le constructeur injecte --version dans les modules empaquetés et
finish.py. Toujours passer explicitement la version lors d’un build.
frontend/package.json décrit l’outil de compilation, pas la version lue
depuis l’agent à l’exécution.

Faire évoluer main par des modifications relisibles. Garder les archives,
clés, états SQLite, résultats de banc et node_modules hors du dépôt. Un tag de
source ou un ZIP GitHub n’est pas un installateur qualifié. Lire PUBLICATION.txt.

10. Ce qu’un prochain développeur doit savoir

Le pilote reconnaît les empreintes d’un bundle précis. Un nouveau Compose,
un nouveau script fournisseur ou une image configurant le réseau nécessite
une nouvelle qualification ; changer une empreinte seule ne suffit pas.

Le réglage de source Git actuel concerne les Releases d’un bundle compatible.
Il ne met pas AquaHub à jour et ne réalise pas un flux fournisseur Git + registre.
Le canal app_updates est implémenté séparément pour les Releases publiques
fixes de mehdi7129/aquahub ; il ne clone ni ne lance un dépôt Git. Voir
API_ET_DONNEES.txt pour ses paramètres et son suivi d’installation séparé
des tâches génériques. Un poste doit déjà être initialisé pour utiliser
le paquet application-only. Aucune Release publique n’est encore annoncée.

WireGuard reste protégé. Les relances de net_setup et gcs_reactor sont
autorisées avec comparaison consultative des adresses/routes ; leurs autres
actions restent protégées. La présence d’un
conteneur running et les deux seules sondes du bundle ne valident pas la
préparation physique des drones. Les contrôles manuels ne sont pas
validés automatiquement.

Les recettes réelles initiales ont été réalisées sur un banc privé. Leurs
identités, configurations et résultats bruts ne sont pas distribués ici.
Reproduire les vérifications sur son propre banc avant de publier un binaire.

11. Reprendre la version 0.2.0

Lire CHANGELOG.md. La progression de configuration est persistée dans la
tâche sous forme d’un objet progress : phase, label, completed, total,
percent et indeterminate. Ses douze jalons reposent sur des observations ;
le temps écoulé n’augmente pas le pourcentage. Pendant le redémarrage,
la barre peut attendre sans que cela signifie une panne. Les cinq rappels
manual_checklist viennent de drone.py et ne valident aucun matériel.

Le téléchargement d’AquaHub utilise également progress, avec phase=download
et completed/total en octets ; l’interface doit afficher des volumes reçus,
pas un nombre d’étapes. L’installation applicative renvoie scheduled puis
se suit avec app_updates.status, car l’agent s’arrête pendant son remplacement.
Après résultat installed, fermer puis rouvrir la fenêtre pour charger
les nouvelles ressources frontend. Ne jamais déduire le succès d’une simple
perte de connexion ou programmer automatiquement une seconde installation.

Le helper système indépendant n’a pas de paramètre fourni par le renderer.
Les tests de ses refus et des paquets sont indispensables avant de publier
un binaire. Une somme SHA-256 GitHub/HTTPS est le contrôle actuel ; elle
n’est pas une signature d’éditeur indépendante. La qualification réelle
d’un nouveau paquet reste distincte des tests de fixtures.

12. Évolutions 0.2.1

En 0.2.1, le précontrôle est devenu accessible sans autorisation interactive
du PC ; configure restait alors soumis à PolicyKit. Le registre sépare
requires_admin de mutation et le précontrôle utilise operation_guard.
Depuis 0.2.4, configure bénéficie aussi d’une délégation explicite au compte
opérateur, tout en gardant les contrôles de cible et de maintenance décrits
en section 15. Le handler de réglages SSH reste soumis à PolicyKit.

Les badges d’état utilisent observationFresh/serviceTone. Le timer de
fraîcheur neutralise un ancien état même si une réponse de l’agent tarde.
La santé reste distincte et un échec de sonde demeure visible.

logs.export renvoie des entrées bornées ; native.export_logs appelle le
dialogue GTK et crée le fichier depuis le compte utilisateur. Voir les
nouveaux modules log_exports.py des deux côtés et test_log_exports.py.
L’export n’a pas besoin de jeton Portainer. Les fenêtres et les données de
recette utilisent exclusivement des fixtures synthétiques ou un banc autorisé.

13. Corrections 0.2.2 et points de vigilance

Le contrat backend progress ne change pas. Dans app.ts, conserver value dès
que percent est défini, même si indeterminate vaut true : celui-ci signale
une attente, pas la perte du pourcentage déjà acquis. Le spinner montre
l’activité sans interpoler l’avancement. ui-webkit.js et le nouveau parcours
run_visual_feedback.py vérifient ce remplissage dans le vrai moteur WebKitGTK.

Les badges utilisent désormais servicePresentation() dans domain.ts : demande
en cours, tâche de relance liée à sa cible, puis attente d’une observation
postérieure à finished_at. status.get fournit déjà collected_at, active_job
et les dernières tâches ; aucune nouvelle API n’est nécessaire. Une réponse
perdue n’autorise pas un second envoi. Le gris conserve l’incertitude ; un
échec de commande ne prouve pas que le conteneur est arrêté. Les tests de
domaine et run_visual_feedback.py couvrent notamment ancien cache, cible
changée, rechargement et suivi perdu.

Le timer de fraîcheur doit comparer l’état effectivement rendu : renderPage()
maintient lastObservationFresh. run_phase1_feedback.py vérifie l’expiration
même si une requête reste bloquée. Ne pas résoudre une intermittence de test
en conservant indéfiniment un badge vert ou en accélérant toute la collecte.

La présentation utilise des contours de 2 px, des titres de mise à jour
communs et des espacements locaux. Le switch de thème a une géométrie
explicite, sans transformation animée. L’artefact signalé n’a pas été reproduit
pendant les captures : ne pas annoncer sa cause comme démontrée. TESTS.txt
décrit les recettes de sources, les essais du paquet et leurs limites.

14. Identité de l’application dans le bureau — 0.2.3

Le correctif est implémenté dans desktop/aquahub_desktop/app.py et les
ressources produites par installer/build_package.py. APPLICATION_ID vaut
com.aquadrone.aquahub et APPLICATION_NAME vaut AquaHub. Définir les noms GLib
avant tout import de Gtk/Gdk : cet import peut initialiser le nom de programme.
Conserver l’icône par défaut pour les erreurs précédant Gtk.Application.

Le lanceur principal conserve son nom de fichier et son icône pour les favoris.
L’assistant GTK4 a sa propre identité .setup et une entrée NoDisplay=true.
StartupWMClass correspond à la classe X11 mesurée ; cette clé ne règle pas
le comportement Wayland. Voir PLAN_IDENTITE_BUREAU_2026-10-21.txt et TESTS.txt
pour les résultats et les limites des observations GNOME.

frontend/tests/run_desktop_identity.py exerce les propriétés natives, l’icône
du candidat dans un thème isolé, un dialogue précoce et deux lancements normaux
dans une session D-Bus/Xvfb privée. Ne pas importer Gtk avant app.main dans
une sonde. --test-script et --quit-after activent NON_UNIQUE : ils ne peuvent
pas démontrer l’instance unique normale. Le mode --package-root ajoute les
lanceurs extraits et l’assistant sans cliquer sur son installation.

Après mise à niveau de 0.2.2, fermer l’ancienne fenêtre puis rouvrir AquaHub.
Ne pas réinitialiser les favoris ou les préférences de session. Le flux
Git + registre du bundle reste le prochain chantier séparé ; ce correctif
ne modifie aucun script fournisseur ni aucune adresse.

15. Configuration sans mot de passe administrateur du PC — 0.2.4

drone.register enregistre preflight et configure avec mutation=True et
requires_admin=False. Ne pas remplacer ce contrat par mutation=False : les
gardes d’opération et de mise à jour doivent rester actives. Le serveur
identifie l’opérateur par SO_PEERCRED et vérifie son UID à chaque dispatch.
Les processus du compte autorisé peuvent invoquer ces méthodes via la socket
privée ; l’autorisation ne dépend pas exclusivement d’un bouton dans la GUI.
La revérification du PID et de son instant de démarrage dans AuthPolicy reste
spécifique aux interventions qui nécessitent PolicyKit.

configure conserve le plan créé par preflight : UID propriétaire, durée
maximale de 600 secondes, usage unique, numéro et identité confirmés. Les
fichiers, réseaux et identité distante sont relus avant l’envoi. Le lancement
passe toujours par submit_job et ses exclusions de maintenance/concurrence.
Les tests doivent exercer le registre réel avec AuthPolicy(privileged=True),
un pkcheck refusé, un transport SSH synthétique et aucun drone physique.
Vérifier aussi les refus de cible, d’UID et de maintenance, ainsi que le maintien
de PolicyKit pour enroll, ssh_settings et les autres interventions protégées.

Ne pas élargir une règle PolicyKit ou sudoers. L’accès SSH déjà configuré est
distinct du mot de passe administrateur du PC ; cette exception ne crée pas
d’accès, n’approuve pas de nouvelle empreinte et ne change ni les scripts
fournisseur ni les IP. Voir SECURITE.txt et API_ET_DONNEES.txt.
