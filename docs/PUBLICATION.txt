AquaHub — construction et publication

1. Trois livraisons différentes

Sources : ce dépôt, licence MIT, sans bundle client ni dépendances vendues.
Application : paquet de mise à jour AquaHub seul, sans bundle ni images.
Kit complet : installateur graphique, runtime, Docker, Portainer et bundle.

Le constructeur propose deux modes distincts. Une mise à jour de l’application
met à jour AquaHub seulement ; l’import d’une archive fournisseur concerne
le bundle Aqua Hub et ses conteneurs. Les sources, authentifications et
conditions de compatibilité de ces deux flux sont indépendantes.

2. Préparer les ressources de l’interface

Depuis frontend/ : npm ci, npm run check, npm test puis npm run build.
Le constructeur exige frontend/dist/index.html, app.js et styles.css.
Le poste de construction nécessite gcc, pkg-config et les en-têtes GTK4.
Les dépendances de construction ne sont pas à installer chez le client.

3. Payload externe

Le dossier fourni à --payload doit contenir au minimum le dépôt APT signé,
sa clé publique, la liste des paquets, les archives d’images du bundle et de
Portainer, bundle.tar.gz, kit.json et SHA256SUMS. La couverture des empreintes
est exacte : un fichier manquant, altéré, ajouté ou lié est rejeté.

scripts/prepare_payload.py prépare un kit PRIVÉ sur un poste déjà équipé.
Il lit les images Docker locales, télécharge la fermeture des dépendances
APT et copie une archive fournisseur externe. Il utilise sudo non interactif,
le contexte Docker default et une clé de signature de recette. Il ne fabrique
pas à lui seul un produit redistribuable ni une identité de publication.
Son option --private-kit est obligatoire. Conserver sa sortie hors du dépôt.

Consulter ses arguments avant utilisation :
  python3 scripts/prepare_payload.py --help

Ne pas utiliser ce script comme installation du poste client. La clé de
recette, le cache, les exports Docker et les configurations restent privés.
Le script ne remplace pas le processus futur de production d’un kit public.

4. Construire un paquet

Pour une mise à jour publique de l’application seule :

  python3 installer/build_package.py \
    --application-only \
    --output dist/aquahub-application_0.2.1_amd64.deb \
    --version 0.2.1

Ce mode n’accepte ni --payload ni --private-kit. Le paquet garde le nom Debian
aquahub-setup afin de mettre à niveau l’installation 0.1.2 existante, sans
migration d’appartenance de fichiers entre deux paquets. Son champ de contrôle
X-AquaHub-Update vaut application-only. Il contient les sources d’exécution,
l’interface, les dialogues et les assistants AquaHub ; aucun kit fournisseur,
export d’image ou configuration du banc n’est ajouté. Les dépendances natives
de l’interface sont déclarées dans le contrôle Debian. Le paquet requiert
une installation AquaHub déjà terminée ; il ne remplace pas le kit complet
pour équiper un nouveau poste. Il peut être installé graphiquement avec le
gestionnaire de paquets Debian ou depuis le bouton de mise à jour AquaHub.

Lors du premier passage d’un kit complet vers ce paquet léger, preinst
arrête uniquement l’agent AquaHub après avoir refusé toute opération active.
Il conserve l’ancien /usr/share/aquahub/offline sous /var/lib/aquahub/offline,
hors des fichiers possédés par dpkg. Ainsi, dpkg peut retirer son ancien
inventaire sans supprimer le kit privé de réparation. Le déplacement conserve
les permissions et les octets. Si /usr et /var sont sur des partitions
différentes, une copie vérifiée par SHA-256 est publiée avant suppression de
l’original ; un manque de place ou deux kits différents interrompent la
migration en conservant les données. L’assistant de réparation sait lire
les deux emplacements. Aucun dossier privé existant n’est rendu public.

Le marqueur setup.complete atteste que l’installation initiale a réussi ;
il n’est plus comparé à la version de l’application à chaque lancement.
Une mise à jour ne doit donc jamais relancer le déploiement du bundle.

Pour un kit complet :

Exemple avec un payload externe déjà vérifié, depuis la racine du dépôt :

  python3 installer/build_package.py \
    --payload /chemin/hors-depot/payload \
    --output dist/aquahub-setup_0.1.2_amd64.deb \
    --version 0.1.2

Cette commande refuse un payload déclaré privé ou contenant les formes de
clés privées reconnues. L’option --private-kit permet uniquement une recette
locale explicitement privée ; elle ne doit pas être ajoutée pour contourner
un refus lors d’une publication publique. Le résultat reste alors privé.

Le constructeur compile les helpers, copie les sources et l’interface,
intègre le payload et produit le .deb. Il n’installe pas ce paquet sur le
poste de construction. Les scripts Debian évitent un apt récursif depuis
postinst ; l’assistant effectue ensuite l’installation hors ligne.

5. Qualifier avant publication

Relier l’artefact à son commit, sa version, ses dépendances et ses empreintes.
Exécuter les tests génériques, puis les recettes réelles de la livraison :
installation GNOME hors ligne, autorisations graphiques, adoption d’un bundle
existant, réinstallation, redémarrage, mise à niveau, désinstallation,
conservation des données et absence de changement des IP existantes.

Vérifier le contenu réel, y compris les archives imbriquées. Un .gitignore
n’est pas un analyseur de secrets et une licence MIT ne donne pas les droits
de redistribuer les configurations ou logiciels d’un fournisseur.
Les notices, sources requises par des licences tierces et droits des images
doivent être traités dans la livraison des composants concernés.

Pour qualifier une mise à jour légère, capturer l’état de la VM après son
démarrage puis avant l’installation du candidat. Comparer après installation
les fichiers du bundle, son unité systemd, le kit hors ligne, les identités,
images, montages et paramètres des conteneurs ainsi que les adresses et routes
IPv4 et IPv6. Un redémarrage de conteneur doit changer son heure de lancement,
sans changer son identité ni son image. Tester les relances autorisées une à
une et conserver les rapports détaillés dans un dossier privé hors du dépôt.
Une recette ne remplace pas la validation d’un comportement fournisseur
encore inconnu : WireGuard demeure protégé tant que son chemin d’échec et
la procédure de reprise ne sont pas validés.

6. GitHub Releases

Dépôt de publication prévu : https://github.com/mehdi7129/aquahub
Ne pas pousser le dépôt privé du banc ou son historique dans ce dépôt public.
Publier une version seulement quand le paquet est qualifié et redistribuable.
Joindre les notes, l’architecture, la version Debian ciblée, les empreintes
et la méthode de vérification de signature retenue. Ne pas joindre un kit privé.

GitHub limite actuellement chaque fichier joint à une Release à moins de
2 Gio. Un gros kit complet doit donc avoir une stratégie de distribution
adaptée ; le futur paquet AquaHub seul doit rester distinct du kit fournisseur.
Cette contrainte ne justifie pas de retirer des fichiers requis du kit hors
ligne. Documentation officielle :
https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases

Une archive de sources automatique de GitHub ne contient ni les dépendances,
ni les images, ni un installateur complet. Ne pas la présenter comme tel.

7. Assistant de mise à jour de l’application

L’agent prépare exclusivement /var/lib/aquahub/agent/app-updates, dossier
root 0700 : package.deb, ready.json, pending.json et status.json sont privés.
pending.json fixe schema=1, version, sha256 et bytes. Après autorisation,
l’agent lance une unité systemd séparée qui exécute sans argument :

  /usr/bin/python3 /usr/lib/aquahub/application-upgrade.py

L’assistant recontrôle propriétaire, permissions, taille (256 Mio maximum), SHA-256, architecture,
nom du paquet, version et X-AquaHub-Update. Il vérifie l’absence de tâche active
et effectue un précontrôle dpkg sans installation ; un échec de dépendance ou
de verrou à ce stade ne coupe pas l’agent. Il arrête ensuite uniquement
aquahub-agent.service, libère le verrou de maintenance pour
le propre preinst de dpkg, puis installe le paquet sans lancer finish.py.
Le processus indépendant reste actif lorsque l’agent est remplacé. Le succès
est enregistré seulement après vérification de la version dpkg, de la version
Python installée et du service actif. En cas d’échec, il tente de redémarrer
l’agent et conserve un état failed et un journal local privé. Les données et
les services fournisseur ne sont pas manipulés par cet assistant.

La version affichée dans une fenêtre déjà ouverte peut rester celle de
l’interface chargée en mémoire : fermer puis rouvrir AquaHub après la réussite.
Ne pas annoncer une restauration automatique de l’application : ce flux
conserve les données mais ne dispose pas d’un paquet précédent automatique.
